# StyleCop review (skill-based, no analyzer package)

This skill performs a StyleCop-style code review by reading C# source and checking
it against a fixed, pragmatic rule set. It exists so the repo gets consistent
`SA####` style feedback on demand **without** referencing `StyleCop.Analyzers` in
any project. There is no build step and no NuGet dependency.

## When to use

- "Check StyleCop on `X`", "run StyleCop", "lint this C#", "style-review this PR".
- Reviewing a file, a folder, the staged diff, or a whole project for style issues.
- Before opening a PR, to catch style problems that no build step flags.

## Scope

1. Analyze `*.cs` files only.
2. **Skip generated code** — do not report on:
   - `*.g.cs`, `*.g.i.cs`, `*.Designer.cs`, `*.AssemblyInfo.cs`
   - anything under a `Migrations/` or `Generated/` folder
   - any file whose first lines contain `// <auto-generated`
3. Default target when none is given: the C# files changed on the current branch
   (`git diff --name-only $(git merge-base HEAD master)...HEAD -- '*.cs'`). If git
   is unavailable, ask the user which path to review.

## How to run the review

1. Resolve the target file list (see Scope).
2. Read each file. For every construct, check it against the rules in
   `references/rules.md`. That file is the source of truth for which rules are
   **enforced (warning)**, **disabled (ignored)**, or **documentation (suggestion)**,
   including short examples of compliant vs. non-compliant code.
3. Record one finding per violation with: file path, line, column (best effort),
   severity, rule id, and the standard StyleCop message.
4. Do not report disabled rules. Report documentation rules as `suggestion`.
5. Never invent violations. If a rule's applicability to a construct is ambiguous,
   omit it rather than guess.

## Output format

Print findings sorted by file, then line:

```
path/To/File.cs(12,5): warning SA1200: Using directive should appear outside a namespace declaration.
path/To/File.cs(20,9): warning SA1516: Elements should be separated by a blank line.
path/To/File.cs(31,5): suggestion SA1600: Elements should be documented.
```

Then two summaries:

```
== Summary by rule ==
SA1200    3
SA1516    2
SA1600    1   (suggestion)

== Summary by file ==
   4  path/To/File.cs
   2  path/To/Other.cs
```

End with the total and a one-line verdict, e.g.
"6 issues (5 warnings, 1 suggestion) across 2 files".

## Fixing

Report only by default. If the user asks to fix, apply the minimal edit that
resolves each finding, re-review, and show the remaining count. Preserve behavior;
never change logic to satisfy a style rule.

## Rule profile

The full catalog with examples lives in `references/rules.md`. Summary:

- **Disabled (ignore):** SA1101 (`this.` prefix), SA1309 (`_camelCase` fields allowed),
  SA1633 (file headers), SA1642/SA1643 (constructor/destructor doc boilerplate),
  SA1413 (trailing commas).
- **Documentation (suggestion, public API only):** SA1600, SA1601, SA1602.
  Private/internal members are not required to be documented.
- **Enforced (warning):** using placement/ordering (SA1200, SA1208, SA1210),
  element ordering (SA1201, SA1202, SA1203, SA1204), layout/readability (SA1028,
  SA1122, SA1400, SA1401, SA1503, SA1516). Other default StyleCop rules may be
  reported as warnings when clearly violated.

This mirrors the "pragmatic clean-architecture" profile: modern C# conventions
(no `this.`, underscore-prefixed private fields, file-scoped namespaces, no file
headers) with ordering, spacing, and public-API documentation kept consistent.
