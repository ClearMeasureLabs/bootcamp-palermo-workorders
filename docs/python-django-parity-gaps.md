# Python Django parity gaps

This prototype remains a staged rewrite. The matrix compares the checked-in Django models and migrations with the current EF Core mappings under `src/DataAccess/Mappings/`. It does not describe an earlier migration snapshot. Source references are `WorkOrderMap.cs`, `EmployeeMap.cs`, `RoleMap.cs`, `WorkOrderAttachmentMap.cs`, and `WorkOrderStatusConverter.cs`.

## Persistence schema matrix

| Area | Current .NET mapping | Django prototype | Gap / effect |
|---|---|---|---|
| Primary keys | UUID keys; Employee, Role, WorkOrder IDs generated by source persistence; attachment ID generated by application | UUID keys for all entities; attachment UUID is supplied explicitly by its service | Key types now match. UUID generation location differs for Employee, Role and WorkOrder. |
| Employee identity | UserName 100, FirstName 100, LastName 120, EmailAddress 255, PreferredLanguage 10 (`en-US` default); all required | Matching column names and widths, UUID key, PreferredLanguage default; required email has no default | Employee field shape and required-value behavior match. |
| Role | Name 100; create/fulfill flags required | Matching names/widths/flags and UUID key | Field shape matches. |
| Employee roles | `EmployeeRoles` table with composite EmployeeId/RoleId primary key | Matching table/UUID FKs/composite primary key | Same key structure; Django uses its default database schema. |
| Work order number | Required string, max length 7; generator takes first seven uppercase GUID characters | Required unique string, max length 7; generated from the UUID key | Format and width now match; uniqueness is enforced in both. |
| Work order title | Required, max length 300 | Required, max length 300 | Field shape matches. |
| Description / instructions | Max length 4000; nullable in EF mapping | Max length 4000; blank values stored as empty strings | Null and empty-string behavior differs. |
| Room | Max length 900; nullable | Max length 900; blank values stored as empty strings | Null and empty-string behavior differs. |
| Status | Three-character codes `DRT`, `ASD`, `IPG`, `CMP`, `CNL` via `WorkOrderStatusConverter` | Matching three-character storage codes with friendly UI labels | Stored codes and width now match. |
| Creator / assignee | Creator FK required; Assignee FK nullable; SQL Server delete action is restricted | Matching UUID FKs, nullability and Django `PROTECT` policy | Django protects ORM deletes, but SQLite's FK pragma stores `NO ACTION`; SQL Server FK actions are not reproduced by the SQLite prototype. |
| Work order dates | CreatedDate, AssignedDate, CompletedDate nullable datetimes; DueDate SQL `date` | Matching nullable date/time fields and date-only due date; CreatedDate defaults to now on normal creates | Column shape matches; CreatedDate default behavior differs. |
| Status history | Current final SQL schema has no WorkOrderEvent table; legacy AuditEntry was removed in migration 020 | `WorkOrderEvent` table stores transitions and notes | Django adds a persistence table beyond the current source schema. |
| Attachment metadata | UUID ID; required WorkOrderId, FileName 500, ContentType 200, FileSize bigint, UploadedById, UploadedDate; work-order delete cascades and uploader delete restricts | Matching column names, UUID FKs, widths, bigint, required fields, and Django `CASCADE`/`PROTECT` policies; UUID and UploadedDate supplied by service | SQLite FK pragma records `NO ACTION`; SQL Server FK actions are not reproduced by the SQLite prototype. Django stores metadata only, no file bytes. |
| Database schemas | Core entities map to `dbo`; migration 022 creates the `[nServiceBus]` schema for transport | Matching table names use the database default schema; no `nServiceBus` schema | SQL Server schema qualification and transport setup are not reproduced. Migration 022 creates a schema, not core tables. |
| Migration history | SQL migrations build final mappings; migration 020 drops legacy AuditEntry | One Django initial migration declares the current prototype schema | The prototype migration history was reset to declare the UUID schema cleanly. Existing prototype databases must be reinitialized or have their data exported and reimported; this initial migration is not an in-place upgrade. |


## Visible UI gaps

The Django shell now has the source's 280px left rail, white top header, centered search heading, result-card treatment, and styled work-order detail card. The current rail omits Counter, Fetch Data, AI Agent, and Settings routes because the Django prototype does not implement those pages. Its footer also does not reproduce the source health/version link. Work-order detail now uses a centered narrow card and read-only fields with status commands; it does not yet reproduce the source's editable title/description/room fields, speech controls, chat panel, or every permission-dependent command state.

The headful acceptance workflow captures login, search, new-order form, and detail views at 1365×900. These screenshots document the current prototype UI; they do not establish full visual or behavioral parity.
